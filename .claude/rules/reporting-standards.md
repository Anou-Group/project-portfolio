# Reporting standards (mandatory)

These rules govern every piece of text a manager can see: project fields, tasks,
issues, activity entries, resource titles and descriptions, and page copy.

## 1. Perspective

The report is written **by Mahesh Pedapati for his manager**. Use an implied first
person with past- or present-tense action verbs.

| Incorrect | Correct |
|---|---|
| Claude analysed the Shopify repository. | Reviewed the Shopify repository and identified outstanding development requirements. |
| I helped Mahesh implement the enquiry forms. | Implemented enquiry forms covering retail, wholesale and supply-contract enquiries. |
| The AI agent identified three issues. | Three outstanding issues were identified during testing. |
| Here are some recommendations for you. | Recommended next steps. |

Technical words such as "AI", "Claude", "automation" or "LLM" are allowed when they
describe the **project** (e.g. "The AI 'ask' box is not built; it needs an
Anthropic API key"). They are never allowed as the actor who did the work.

## 2. Prohibited content

- AI self-references, "as an AI", "I'm an assistant".
- Internal reasoning, scratchpads, `<thinking>`, chain of thought, prompts or
  instructions to a model.
- Conversations between Mahesh and an assistant; "let me", "I'll", "hope this
  helps", "here are", "feel free", "great question".
- "Generated by …" footers copied from pull requests or tools.
- Debugging commentary, TODO/FIXME/TBD markers, lorem ipsum.
- Unverified claims ("fully tested", "production-ready", "100%") without evidence.
- Private implementation discussion that does not help the manager.

## 3. Status vocabulary

| Status | Use when |
|---|---|
| **Completed** | The work is finished and evidence exists (merged PR, tracker marked Done, document sent). |
| **In Progress** | Work has started and is not finished. |
| **Pending** | Planned or awaiting commencement. |
| **Blocked** | Cannot progress because of a dependency or obstacle. |
| **Awaiting Approval** | A decision or approval by someone else is required. |

- "Merged to the preview (dev) theme" ≠ "live". "Built" ≠ "tested" ≠ "deployed".
  Say which one is true.
- A Completed task **must** carry `evidence` (where the proof is) and should carry
  `completedAt`. If the date is unknown leave it empty — the UI says "Date not recorded".
- Statuses from other tools are mapped: Notion "Done" → Completed; "In progress" →
  In Progress; "Testing" → In Progress with "in testing" in the latest progress;
  "Not started" → Pending; "Blocked" → Blocked.

## 4. Evidence and unknowns

- Acceptable evidence: GitHub commits, branches and pull requests; Notion tracker,
  decision log and work log entries; project plan documents in the repository;
  documents or confirmations supplied by the owner.
- Not evidence: an AI conversation, a plan that was never executed, a branch that
  was never merged.
- Unknown values are written exactly as `Pending confirmation`. Do not use TBC,
  N/A or "unknown" in manager-facing text.
- Every URL must be one that was opened or returned by the source system. Never
  construct or guess a URL.
- Record where status came from in the project's `sourceNote`
  (e.g. "Phase 1 tracker last updated 27 Oct 2026; GitHub to 8 Nov 2026").

## 5. Responsibilities

- Tasks are Mahesh's own work. Things other people must decide, supply or approve
  are `issues` (kind `decision`, `approval`, `dependency` or `blocker`) with
  `waitingOn` naming the person or team.
- Do not add stakeholders, approvals or decisions that are not documented.

## 6. History

- Never delete a task, issue, update or project. Change its status, or set
  `isPublished: false` if it must be hidden; the database blocks deletes.
- When a task moves to Completed: keep its description and evidence, set
  `completedAt` if known, add an activity entry, and leave earlier activity alone.
  The database records the status change in `task_status_history`.
- Resolve issues by setting `status: "resolved"` and `resolvedOn`, not by removal.

## 7. Style

- Plain, concise, non-technical first; technical detail only where it adds value.
- Australian English spelling (organisation, colour, catalogue).
- Dates as ISO in content (`2026-10-22`); the UI formats them ("22 Oct 2026").
- Activity entries say what changed; do not repeat the project description.

## 8. Enforcement

`npm run content:check` runs deterministic checks (schema, statuses, required
fields, resource labels, evidence for completed work, dates, references) and a
contextual language lint. **Errors block publishing. Warnings require a human read**
— the lint deliberately does not reject legitimate technical uses of words like
"AI" or "Claude"; it flags them for review. The final check is the review step in
the `project-reporting` skill.
